# Release assets: Swift off git, and a C distribution

Written 2026-10-29 from ROADMAP items "Swift: remote `binaryTarget`" (Phase 2) and "C" (Phase 3),
after a local spike and a survey of the Forge's staging and release code. The owner approved
the direction the same day ("I'm fine with the swift re-design, 2 & 3. I trust your judgement I
just want one way to get the version number"). Spans HyperUuid and the Forge
(`SkunkWerkx/.github`); every Forge change is opt-in through `.github/hyper.json`, so HyperCast
and HyperTabular, frozen until HyperUuid 1.1 ships, see none of it.

## Goal

- Swift consumers get the core from two zips attached to the GitHub Release, named by URL and
  checksum in `Package.swift`, instead of 14 archives and an xcframework committed to git.
- C (and through it C++ and every language with a C FFI) gets a real distribution: one
  generated header, prebuilt shared and static libraries per platform, pkg-config and CMake
  package files, attached to the same GitHub Release and covered by the same attestations.
- Both ride one new piece of release plumbing: a `github` group in the release inventory,
  whose files become GitHub Release assets. PHP's PIE zips and Go's archives can use it later.

## Decisions

- **One way to get the version: `hyperuuid_version()`,** the export every binding already
  calls (packed `major << 16 | minor << 8 | patch`). No header macro, no new export, no
  versioned soname. The ABI contract is the crate's semver: a minor release may add exports,
  only a major may change or remove one. pkg-config's `Version:` and CMake's
  `ConfigVersion.cmake` carry the same number because those tools need it to resolve
  `find_package(hyperuuid 1.1)`; they are generated from `rust/Cargo.toml`, never written by
  hand, and are build metadata, not something a program asks.
- **The header is generated by cbindgen** from `rust/src/ffi.rs`'s doc comments, committed at
  `include/hyperuuid.h`, and a test (`rust/tests/header.rs`, cbindgen as a dev-dependency)
  regenerates it and fails on any diff. The Swift bundle's `include/hyperuuid.h` stays, as a
  generated copy the same test holds byte-identical, because the bundle zip and the Forge's
  ABI probe read it there. The hand-written header it replaces had already drifted (it never mentions return code 6,
  "the v7 stream cannot advance", which `ffi.rs` documents). R's `r/src/core.h` stays, still
  checked against the export set by `check_exports.py`, because the R tarball is
  self-contained and its one-prototype-per-line rule is what that check parses.
- **The Swift zips are built in ci.yml, not at tag time.** Their checksums must be in
  `Package.swift` at the tagged commit B, and B is written by staging, before the tag. So
  `hyper-build-static.yml` zips the bundle and the xcframework it just built and attests them,
  like every other native. Staging verifies those attestations and writes the two checksums
  and the version into `Package.swift`; the tag run compares, and the release attaches the
  same bytes. Nothing has to be byte-reproducible.
- **The C archives are packed at tag time,** by a new `pack-c` composite action in release.yml,
  from the CI run's attested `native-*` and `static-libs` artifacts, the way `pack-gems`,
  `pack-npm` and `pack-r` work. Nothing in B depends on their bytes.
- **The root manifest reads a local bundle when one is there.** CI and local builds write
  `swift/HyperUuidCore.artifactbundle/` (archives and `info.json`, now gitignored); when its
  `info.json` exists, `Package.swift` uses the path, otherwise the release URL. A consumer's
  checkout never has one (gitignored), so it always takes the URL; CI's smoke tests link the
  core the run just built, with no environment switch. `HYPERUUID_LOCAL_CORE` and the core
  freshness test go: `local-core.sh` writes the host's archive into the in-tree bundle, so a
  stale committed core can no longer be what the suite runs against.
- **macOS dylib install name `@rpath/libhyperuuid.dylib`.** Today it is the CI runner's
  absolute build path (`otool -D`), harmless to bindings that open the library by path and
  fatal to a C program that links against it. Linux's and Android's shared library gets the
  plain soname `libhyperuuid.so` (unversioned, per the first decision). Both are set by the
  crate's `rust/build.rs` for the `cdylib` feature, not by the Forge, so they reach the
  siblings only when they cascade.
- **Windows ships the import library.** A C program linking `hyperuuid.dll` needs
  `hyperuuid.dll.lib`, which the `native-win-*` artifacts drop today. It travels as its own
  attested artifact behind `c_assets`, not inside `native-win-*`: every packer copies that
  artifact whole (NuGet's `runtimes/{rid}/native/`, the gems, PHP's staging), and none of
  them should ship it. The static library keeps its name, `hyperuuid.lib`.

## The spike (2026-10-29)

`.binaryTarget(url:checksum:)` pointing at zips of today's bundle and xcframework, with no
binaries in the tree:

| Leg | Result |
|---|---|
| macOS `swift test` (6.4) | 64 tests pass |
| glibc, Static Linux musl, wasm (6.2.4, the floor; and 6.4.1) | download over https, link, run |
| iOS device, iOS simulator, Mac Catalyst (Xcode) | build; Catalyst binary runs, core linked |
| One checksum digit changed | build stops: checksum mismatch |

Not run locally: Windows and Android (CI's legs cover them). SwiftPM caches artifacts by URL,
so bytes behind a released URL can never change for a client that has fetched them; GitHub's
immutable releases keep the server side the same.

## What ships

GitHub Release `vX.Y.Z`, beside `inventory.json`:

- `HyperUuidCore.artifactbundle.zip`: today's bundle, 11 triples, `info.json`, `include/`
  (generated header, module map).
- `HyperUuidCoreApple.xcframework.zip`: the three arm64 slices.
- `hyperuuid-X.Y.Z-<rid>.tar.gz` (`.zip` on Windows), one per RID: linux-x64, linux-arm64,
  linux-musl-x64, linux-musl-arm64, osx-x64, osx-arm64, win-x64, win-arm64, android-arm64,
  android-x64, ios-arm64, iossimulator-arm64, maccatalyst-arm64, maccatalyst-x64 and
  wasi-wasm32 (the last five static only; iOS added 2026-10-29 for parity). Layout:

  ```
  include/hyperuuid.h
  lib/libhyperuuid.a                      (Windows: lib/hyperuuid.lib)
  lib/libhyperuuid.so | .dylib            (Windows: bin/hyperuuid.dll, lib/hyperuuid.dll.lib)
  lib/pkgconfig/hyperuuid.pc              (relocatable: prefix=${pcfiledir}/../..)
  lib/cmake/hyperuuid/hyperuuidConfig.cmake, hyperuuidConfigVersion.cmake
  LICENSE, README.md
  ```

  CMake targets `hyperuuid::hyperuuid` (shared) and `hyperuuid::hyperuuid_static`, with the
  static library's system dependencies as interface links (Windows: `bcryptprimitives` for
  `ProcessPrng`; verified per platform by the smoke test, not assumed).

## Where the changes land

**HyperUuid**
- `rust/cbindgen.toml` and `include/hyperuuid.h`; `ffi.rs` doc comments written for C readers
  (no rustdoc link syntax). Rust-only constants excluded.
- `Package.swift`: URL + checksum targets, the local-bundle switch; `swift/Package.swift`:
  always the in-tree bundle. `.gitignore` the bundle's archives and `info.json`; delete the
  committed ones and the xcframework.
- `swift/HyperUuidCore.artifactbundle/include/`: the module map and the generated header copy.
- `c/`: the pkg-config and CMake templates, the C README, and `c/smoke/` (a consumer built
  through `find_package` and through `pkg-config`, shared and static), formatted by
  clang-format like `r/src`.
- `.github/hyper.json`: `"swift_remote": true`, `"c_assets": true`.
- `release.yml`: `pack-c` job; `publication-gate` gains the `github` group.
- `check_exports.py`: the generated header is a site; the Swift bundle header site goes.
- Tests: `test_abi_probe.py`'s include path; workflow contracts for the new jobs.
- READMEs: Swift install (nothing changes for consumers but the bytes' home), a C section,
  `swift/README.md`'s development loop, CLAUDE.md's never-hand-edit and local-loop lists.
  CHANGELOG under Unreleased.

**Forge** (all behind the flags; defaults keep today's behaviour)
- `hyper_config.py`: `swift_remote`, `c_assets`. With `swift_remote`, the bundle and xcframework leave `payload_paths`, `payload_trees` and
  `STATIC_TREES`, and the root `Package.swift` joins the paths staging may change.
- `hyper-build-static.yml` / `static-libs`: copy the header in from `header`; with
  `swift_remote`, zip the bundle and xcframework into a `swift-release-assets` artifact and
  attest it.
- `hyper-build-native.yml`: with `c_assets`, the Windows import library as its own attested
  artifact.
- `hyper-stage-natives.yml`: with `swift_remote`, verify the zips' attestations and rewrite
  `Package.swift`'s version and checksums (one small script, tested) instead of staging the
  Swift trees.
- `release_guard.py`: validate the `Package.swift` rewrite in the A→B transition, and on the
  tag compare its checksums with the CI run's zips.
- `actions/pack-c` (new): build the per-RID archives, generate `.pc` and CMake files from the
  version, smoke-link each archive on the runner that can run it.
- `release_inventory.py`: a `github` group with its layout from the flags; `finalize` attaches
  every `github/` file with `gh release create`/`upload`, byte-identical on a re-run like
  `inventory.json`. `release_notes.py`: the asset list instead of "committed for Swift".
- Tests beside each (`test_hyper_config.py`, `test_release_guard.py`,
  `test_release_inventory.py`, `test_release_finalization.py`, `test_forge_producers.py`).

## Order of work

1. Header: cbindgen, `include/hyperuuid.h`, the regenerate check, `check_exports.py`. HyperUuid
   only; proven locally.
2. The macOS install name and Linux soname (`rust/build.rs`; a no-op for every binding that
   opens by path). Done 2026-10-29: a C program linked against either runs from a relocated
   directory, and without the build script it does not. The Windows import library moves to
   step 4, behind `c_assets`.
3. Swift: manifests, gitignore, Forge static-libs zips, staging rewrite, guard. The HyperUuid
   half went first, at the owner's ask (2026-10-29): the binaries leave the tree before the
   Forge can stage the zips, so the Forge half must land before the next release; CI needs
   none of it, since every leg builds its own core.
4. C: templates, smoke test, `pack-c`.
5. Inventory `github` group, finalize, release notes.
6. Docs, CHANGELOG, ROADMAP.

What only CI can prove: Windows and Android Swift legs, the attestation steps, staging and the
release dry run. The first real proof of the release half is 1.1.0's own tag run.
