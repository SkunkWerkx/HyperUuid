# Java 21 (JNI base, multi-release jar) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One jar, `io.github.skunkwerkx:hyperuuid`, runs on JDK 21 and later. It reaches the core through JNI on 21–24 and through FFM on 25+, with one API, the same exceptions and messages, and one core.

**Architecture:**
- **`java/jni/`:** a binding-owned no_std Rust cdylib. It links the core statically and registers 14 natives eagerly from `JNI_OnLoad`.
- **The Java side:** a package-private `NativeCore` in two trees. The base (`--release 21`) is JNI. `src/main/java25`, under `META-INF/versions/25`, holds today's FFM code moved unchanged. `UuidGenerator` keeps every check and every rc mapping.
- **CI:** the Forge gains inputs that default off, for the JNI build, its suites and its attestations, then this repo turns them on.

**Tech Stack:** Rust (edition 2024), `jni-sys` 0.4, `no-panic`; Gradle 9.8.2 on JDK 25 with a JDK 21 launcher; JUnit 6; GraalVM CE 25; the Forge's `hyper-build-native.yml`, `hyper-check-core.yml` and `prepare-maven-package`.

**Spec:** `docs/superpowers/specs/2026-10-28-java21-jni-design.md`. This is plan 4 of 5 for Phase 1; the order is in `docs/superpowers/brainstorm/2026-10-28-phase1/integration.md`.

## Global Constraints

- **Floor:** `val jdkFloor = 21` in `java/build.gradle.kts` is its single source. The base compiles with `--release 21` and `java25` with `--release 25`. Gradle, Spotless, javadoc and publish run on JDK 25 only.
- **Why not 17**, stated first in both READMEs: Temurin ships no JDK 17 for Windows arm64 or Alpine (musl) arm64 (Adoptium API, checked 2026-10-28), and 17 leaves Temurin support on 2027-10-31.
- **Drop date:** JDK 21 reaches EOL at Temurin on 2029-12-31. It is recorded in CLAUDE.md, the way Ruby 3.4's is.
- **Crate:** `hyperuuid-jni` 0.0.0, `publish = false`, `[lib] name = "hyperuuid_jni"`, `#![cfg_attr(not(test), no_std)]`, no `alloc`.
  - **Normal dependencies:** `hyperuuid = { path = "../../rust", default-features = false, features = ["cdylib"] }` and `jni-sys = "0.4"`.
  - **Dev-dependency:** the same `hyperuuid` with `features = ["cdylib", "std"]`.
  - **Profiles:** `panic = "abort"` in both, for every shipping build. Release adds `lto = true`, `codegen-units = 1` and `strip = true`.
  - **The no-panic proof alone builds with unwind:** `CARGO_PROFILE_RELEASE_PANIC=unwind cargo build --release --locked --example no_panic --features no-panic`. Under abort, no-panic cannot see a panic path: a runtime-dependent `.unwrap()` links clean (measured, on macOS and in `rust:latest`). The core's proof works the same way, because `rust/Cargo.toml`'s `[profile.release]` sets no `panic` and so unwinds.
  - `Cargo.lock` is committed.
- **C imports:** `malloc` and `free` are declared in the shim's own `unsafe extern "C"` block, beside the 13 core exports. There is no `libc` dependency.
- **Registration:** `JNI_OnLoad` is the shim's one `#[no_mangle]` item. It calls `RegisterNatives` on `io/github/skunkwerkx/hyperuuid/NativeCore` with one table of 14 entries.
  - `jniNatives` returns the table's length, never a literal.
  - A `const` assertion fails the build on a repeated name.
  - Table entries are matched, never unwrapped.
- **Critical regions:** `CRITICAL_MAX = 64 * 1024` bytes. Only the core call runs inside one.
  - Above the cap, a v5 name goes through `GetByteArrayRegion` into `malloc`.
  - A batch is one core call into `malloc`, then `SetByteArrayRegion` in 1 MiB chunks.
  - The buffer is freed on every path. A zero length passes null and pins nothing.
- **A null array access** (a critical get or `malloc`) is never mapped as a core result. With `ExceptionCheck` true, the shim returns at once. Otherwise it calls `ThrowNew(java/lang/OutOfMemoryError)`.
- **Messages:** the mapping lives only in `UuidGenerator`. Only two texts differ by path:
  - the stale-library cause: FFM `libhyperuuid does not export <s>`, and JNI `libhyperuuid_jni implements <n> natives; this binding declares <m>` or the error `System.load` threw;
  - FFM's `AssertionError` around `invokeExact`.
- **Resources:** `/native/{rid}/` holds `libhyperuuid.{so,dylib}`/`hyperuuid.dll` and `libhyperuuid_jni.{so,dylib}`/`hyperuuid_jni.dll`.
- **Forge:** one PR, merged first, every new input off by default. It is never merged while a release is in flight. The JNI steps go ahead of TypeScript, the fail-fast rule (CLAUDE.md "Forge coupling").
- **Git:** the owner drives it. Implementers stage nothing and commit nothing; the work stays in the working tree. Forge edits stay in the `../HyperForge` working tree.
- **Docs:** READMEs state the current state, and history goes in the CHANGELOG. Install snippets keep `<version>`. README examples are run by hand.
- **Receipts:** no table, figure or machine label changes in this plan. They belong to the system-wide M6 receipts pass (see "Deferred to the receipts pass"). The spec's sentence "on macOS, the core calls `getentropy` for every id, which dominates…" and its audit row are struck: Apple entropy replaces that syscall.
- **Checks:** every check runs with its negative control (NC), and flags are copied from the CI step or alias it mirrors. Local JDKs: Temurin `~/.sdkman/candidates/java/21.0.13.0+9-tem` and `25.0.5.0+8-tem`, and GraalVM `25.4.4.1+1-graalce`. Below, `$FLOOR` is the first path.
- **Scratch copies** for negative controls live in the session scratchpad, never in the tree.
- **Formatting:** `spotlessCheck` covers `src/main/java25`. In `java/jni`, `cargo fmt --check` and `cargo clippy --release --locked --all-targets -- -D warnings` stay clean.

## Spec corrections found while planning

1. **`crate-type = ["cdylib"]` alone cannot feed the no-panic example.** Measured in a scratch crate: the example fails with E0433, "cannot find module or crate `hyperuuid_jni`". The plan uses `crate-type = ["cdylib", "rlib"]`.
   - The osx-arm64 cdylib is 50,688 bytes against 50,672 with cdylib alone, so LTO still applies.
   - The natives are `pub unsafe extern "system" fn`. As `pub` fns taking raw pointers, they would otherwise fail clippy's `not_unsafe_ptr_arg_deref` (measured).
2. **A failed `RegisterNatives` surfaces from `System.load` as `NoSuchMethodError`, not `UnsatisfiedLinkError`.** Measured on Temurin 21.0.13 and 25.0.5 with a mistyped descriptor: `java.lang.NoSuchMethodError: Method 'int P.uuidNewV4(int[])' name or signature does not match`. The JDK rethrows the exception that `JNI_OnLoad` left pending. The JNI stale-library cause is therefore that error.
3. **L2's negative control is visible only on Linux.** On macOS, `resolver = "1"` passes `feature="std"` to the core's rustc (seen with `-v`), yet the dylib keeps the same size and the same `otool -L` (libSystem, libiconv), with no std strings. On glibc Linux (`rust:latest`) the same change adds `NEEDED libgcc_s.so.1`. L2 and its NC therefore run in a Linux container locally, and in `lint-java-jni` in CI.
4. **The facade name `hyperuuidVersion()` collides with the JNI native `hyperuuidVersion()I`.** The 13 natives are `camel(export)`, which `check_exports` pins. The JNI facade must touch the load holder before calling the native, so the two cannot be one method. The facade is renamed `coreVersion()` in both trees. The other facade names differ from their natives (`newV4` against `uuidNewV4`).
5. **Line references drifted.** Use the text anchors below, not these numbers.
   - The Forge's Java steps are at `hyper-build-native.yml:906-953` (spec: :905-940).
   - The core's panic handler and personality stub are at `rust/src/lib.rs:59` and `:91` (spec: :56 and :88).
   - `ci.yml`'s check-core `with:` ends at `lint_r: true` (:208), not :204.
6. **`jni-sys` 0.4 is not quite "types only".** It pulls in `jni-sys-macros`, a proc-macro on `syn`, at build time, so the lock carries those crates. Its `JNINativeInterface_` is `#[non_exhaustive]` and a versioned union (`(**env).v1_2.X`), so the unit tests cannot build one with a struct literal. They build a stub in a `MaybeUninit`; see Task 2.

## Review Focus

1. **Either side of the 64 KiB bound.** A batch of 4,096 UUIDs (critical) and of 4,097 (malloc), and v5 names of 65,536 and 65,537 bytes, must give the same results as on FFM. Pinned in Task 5's `fillsEitherSideOfTheCriticalBoundAreWhole`, and v5 against a `MessageDigest` SHA-1 reference.
2. **A shaded jar that lost `Multi-Release` on JDK 25.** The README calls the JNI path there "correct but slower". Pinned in Task 5's `BackendTest.aStrippedJarRunsJniCorrectlyOn25`: a child JVM, on the jar copy with the attribute stripped, reports `jni`, passes the corpus doors, and its warning names `System::load`.
3. **Two class loaders in one JVM.** JNI refuses one library in two loaders. Each extracts its own temp copy, so both must report `isAvailable()`. Pinned in Task 5's `BackendTest.twoClassLoadersEachLoadTheCore`.
4. **The module path.** Run with `--module-path <jar> --enable-native-access=io.github.skunkwerkx.hyperuuid`, the expected backend loads and nothing is printed. Pinned in Task 5's `BackendTest.theModulePathLoadsTheExpectedBackend`.
5. **A racing first touch.** Thirty-two threads hit different doors first in a fresh JVM. Exactly one load happens and every door succeeds. Pinned in Task 5's `BackendTest.aRacingFirstTouchLoadsOnce`, in a child JVM.
