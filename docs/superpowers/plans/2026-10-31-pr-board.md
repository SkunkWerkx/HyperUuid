# The PR board: core first, host × binding, only what changed — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the 84-job pull-request board with a core-first grid that runs each binding only when it changed, lints each binding once, and keeps every artifact name the release side downloads.

**Architecture:** The Forge (`../HyperForge`, `SkunkWerkx/.github`) gains new reusable workflows beside its existing ones: one core workflow with the seven host legs, one lint workflow and one test workflow per binding, and a three-host core-checks workflow. This repo's `ci.yml` becomes a `changes` classifier, one caller per workflow gated on its outputs, and a `pr-board` aggregate. Nothing the siblings call changes behaviour at today's inputs; the old workflows go only after HyperCast and HyperTabular move.

**Tech Stack:** GitHub Actions reusable workflows and composite actions; Python 3 `unittest` shape tests (`yaml_lite` in the Forge, regex-on-text in this repo); `gh api` for the pull-request file list.

**Spec:** `docs/superpowers/specs/2026-10-31-pr-board-design.md`

Revised 2026-10-31 after a review of the first draft (thirty findings, all verified; the Revision log at the end lists them).

## Global Constraints

- Runner labels, verbatim, in every `runs-on` and every matrix `os:` list this plan creates or edits: `ubuntu-26.04`, `ubuntu-26.04-arm`, `xcode-27`, `windows-2025-vs2026`, `windows-11-vs2026-arm`. The label shape tests read `runs-on:` values and matrix `os:` lists only, never the whole file (`bun-version: latest` and comments naming `macos-latest` exist and are fine). The spec's one permitted exception, the win-arm64 Swift leg on `windows-11-arm` if VS 2026 breaks it, is taken by adding a commented entry to the test's allow-list in the same change.
- Every artifact name in the spec's Release contract keeps its name and content and has exactly one producing job: `native-<rid>`, `native-android-<arch>`, `static-libs`, `swift-release-assets`, `jni-<rid>`, `node-<rid>`, `node-wasm32-wasip1`, `ruby-native-<rid>-<abi>`, `ruby-wasm-<abi>`, `php-ext-<rid>-<minor>`, `pypi-wheels-*`, the wasm archive, `aot-report-<rid>`, `c-packages-ci`.
- Every attestation step keeps `inputs.mode != 'pr'` in its `if:`, and every caller of a workflow that contains an `Attest` step grants `id-token: write` and `attestations: write` (as today's `build-native` caller does at `ci.yml` lines 102–105).
- `mode` is passed to every Forge call that declares it, always as `${{ github.event_name == 'pull_request' && 'pr' || 'release' }}`.
- Third-party actions are pinned to a commit with the version in a trailing comment; Forge calls are `@master`. Copy each `uses:` line from the workflow the step came from.
- Existing Forge workflows and composites (`hyper-build-native.yml`, `hyper-check-core.yml`, `hyper-test-c.yml`, `hyper-build-php-extension.yml`, `musl-native`) change only by additive, defaulted inputs; their behaviour at today's inputs is unchanged and their existing tests keep passing.
- The owner drives git: no task commits, pushes or dispatches. Each task ends with the work verified in the tree and reported ("stop for the owner").
- Forge tests run from `../HyperForge` as `python3 .github/scripts/test_<name>.py`, unpiped. This repo's shape tests run from the repo root as `python3 .github/scripts/tests/test_<name>.py`, unpiped.
- A verification counts only when its negative control fails.

## Review Focus

1. A pull request from a fork: `changes` must classify with the default read token, and no attestation step may run. Test in Tasks 9 and 10.
2. A pull request that only renames a file out of `rust/` into `docs/`: `core` true and `docs_only` false. Test in Task 9.
3. A pull request touching an unlisted path, an empty file list, or a list at the API's 3,000-file cap: the full board. Test in Task 9.
4. A binding's lint fails while its suites would pass: every `test-<binding>` leg skipped, `pr-board` red naming the lint. Test in Task 10.
5. Release mode (`workflow_dispatch`, `schedule`): `docs_only` false and every other key true, `core` runs, every artifact present under its old name, `request-staging` fires. Tests in Tasks 8, 9, 10 and the dispatched board in Task 13.

- `classify(paths: list[tuple[str, str | None]]) -> dict[str, bool]`: keys `core, ci, docs_only, csharp, java, python, ruby, php, swift, typescript, r, go`. Matcher semantics: a rule is `<dir>/**` (prefix match on `<dir>/`), `**/*.<ext>` (suffix match at any depth, root included), or an exact path. Rules and precedence are the spec's table, `ci` first. A rename contributes both paths. `everything` (an unclassified path, or an empty list, or a list of 3,000 or more entries, the API's cap) sets every key true and `docs_only` false. `core` sets every binding true. `docs_only` is true only when every path is docs or dotfiles.
- `main(argv)`: reads `filename\tprevious_filename` lines on stdin (empty second field for none) and prints `key=true|false` lines; `--all` prints every key true and `docs_only=false` (release mode). Exit code 0 only when every key was printed.

```bash
set -euo pipefail
if [ "${GITHUB_EVENT_NAME}" = pull_request ]; then
  gh api "repos/${GITHUB_REPOSITORY}/pulls/${PR}/files" --paginate \
    --jq '.[] | [.filename, (.previous_filename // "")] | @tsv' \
    | python3 .github/scripts/pr_changes.py | tee -a "$GITHUB_OUTPUT"
else
  python3 .github/scripts/pr_changes.py --all | tee -a "$GITHUB_OUTPUT"
fi
```

  and `outputs:` mapping each key to `${{ steps.classify.outputs.<key> }}`. Under `pipefail` an API failure fails the job, and a job that failed to classify is red, not docs-only.
